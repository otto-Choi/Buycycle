# Buycycle 구현 계획: ISA ETF 월초 자동 적립 매수 시스템

## Context
한국투자증권(KIS) Open API로 ISA 계좌의 ETF를 매달 초에 목표 비중에 맞춰 자동 매수한다.

확정 사항
- 스택: Python(FastAPI), SQLite + SQLAlchemy, React, OS 스케줄러
- 구조: API 서버와 작업 명령(월초 자동매수 등) 두 프로세스로 분리한다. 같은 서비스 코드를 쓰고, 작업 명령은 OS 스케줄러가 호출한다.
- 실행 환경: 내 PC로 시작한다. 이후 서버 이전을 검토한다.
- LLM은 사용하지 않는다.
- 주문: 완전 자동, 매수만으로 비중 맞춤, 모의투자 우선(실전은 명시적 전환)
- 월 기본 투자금 150만원, 여윳돈 추가 납입 가능
- 알림: 텔레그램 봇 (매수 계획, 매수 직전, 체결)
- 참고 자료: 증권사 배포 코드를 `docs/reference/`에 두고 git에서 제외한다.
- 진행 방식: 가장 작은 단위부터 실제로 구현하고 점차 확장

## 진행 원칙
- 각 단계는 단독으로 실행·검증 가능해야 한다. 이전 단계가 끝나기 전에 다음 단계의 코드를 만들지 않는다.
- 주문과 관련된 코드는 항상 기본값이 모의/dry-run이다.
- 안전장치(주문 상한, 중복 방지)는 하네스가 아니라 프로그램 코드에 둔다.

## 단계별 계획

### 0단계: 준비 (완료)
- KIS API 참고 코드를 `docs/reference/`에 배치, `.gitignore`에 추가.
- ISA 계좌 API 주문 지원 여부 확인 완료.
- 모의투자 앱키 발급, `.env.example` 작성은 해당 단계에서 진행한다.

### 1단계: 기술 스택과 프로젝트 뼈대
설계와 구현의 기반이 되는 부분이라 가장 먼저 구성한다.
- 확정: Python, FastAPI, SQLite + SQLAlchemy, React, OS 스케줄러
- 제안(미확정): 패키지 관리 uv, pytest, ruff, pydantic-settings, Vite + TypeScript. HTTP 클라이언트는 참고 코드(`docs/reference/`)가 쓰는 라이브러리를 확인해 정한다.
- 설정: `.env`, `TRADING_MODE`(기본 `paper`)
- 산출: `backend/pyproject.toml`, 빈 테스트가 통과하는 pytest, `/health` 엔드포인트, `backend/src/jobs/`(작업 명령 진입점), DB 모델 골격(목표 비중, 납입, 주문, 체결, 실행)
- 확정 후 `.claude/rules/backend.md`, `frontend.md` 본문을 작성하고 `docs/decisions.md`에 기록한다.

### 2단계: 매수 계획 계산 (네트워크 없음)
`backend/src/rebalance/plan.py`의 순수 함수 `build_plan(targets, holdings, prices, cash)`. 아래 알고리즘을 그대로 코드화한다.

입력: 목표비중 w_i, 현재 보유금액 v_i, 주당가격 p_i, 투입 현금 C

1. 총액 T = Σv_i + C (고정)
2. 종목별 목표금액 t_i = T × w_i
3. 종목별 매수량 q_i = 0으로 시작한다.
4. 다음을 반복한다.
   - 후보: 잔여 현금 ≥ p_i 인 종목
   - 종목별 개선량 = (v_i - t_i)² - (v_i + p_i - t_i)². 부족금액 t_i - v_i 가 p_i/2 보다 클 때만 양수다.
   - 개선량이 양수인 후보가 없으면 종료한다.
   - 개선량이 가장 큰 종목을 1주 매수한다(q_i += 1, v_i += p_i, 잔여 현금 -= p_i). 동률이면 종목코드 오름차순.
5. 출력: 종목별 매수량, 예상 매수금액, 매수 후 예상 비중, 잔여 현금

- 초과 보유 종목은 개선량이 항상 0 이하라 자동으로 매수에서 제외된다. 매도는 하지 않는다.
- 부족금액이 주당가격의 절반을 넘을 때만 매수하므로 목표를 크게 넘겨 사지 않는다.
- 잔여 현금은 다음 달 투입 현금에 이월된다.
- 입력은 `input/targets.csv`(종목코드, 목표비중). 비중 합이 100%가 아니면 오류.
- 단위 테스트: 모든 종목이 부족, 일부 초과(자동 제외), 부족금액이 주당가격 절반 미만이면 매수 안 함, 현금 부족으로 중단, 동률 처리, 비중 합 오류.
- 하드코딩 시세와 보유 데이터로 계획을 출력하는 간단한 CLI.

### 3단계: 텔레그램 알림
- `backend/src/notify/`에 `Notifier` 인터페이스와 `TelegramNotifier`. 후에 다른 채널을 추가할 수 있게 분리한다.
- 메시지 3종: ① 매수 계획(종목별 예상 매수금액, 현재/목표/예상 비중) ② 매수 직전 알림 ③ 체결 알림.
- 2단계 CLI의 계획을 텔레그램으로 전송해 확인한다.

### 4단계: KIS 읽기 전용 연동 (모의)
- `backend/src/broker/kis.py`: 토큰 발급/캐시/갱신, 잔고 조회, 현재가 조회. 참고 코드는 `docs/reference/`.
- 하드코딩 데이터를 실제 모의계좌의 잔고와 시세로 교체해 계획을 산출한다.

### 5단계: 주문 실행 (모의투자)
- 주문과 체결 조회를 추가한다.
- 안전장치
  - 기본 `paper`. `live`는 `TRADING_MODE=live`와 별도 확인 플래그가 모두 있어야 한다.
  - 1회 총 주문금액 상한, 종목별 상한. 초과 시 주문하지 않고 알림.
- 중복 실행 방지
  - 실행 기록에 종류(`auto`/`manual`)를 구분해 저장한다.
  - 중복 방지 키는 (연월, `auto`)이다. 자동매수가 한 번 실행되었어도 수동매수는 막지 않는다. 수동매수에는 같은 요청의 중복 제출만 막는 요청 단위 키를 둔다.
  - 판단 기준은 실행 기록이 아니라 **체결 기록**이다. 주문별 주문번호, 체결수량, 체결가, 상태를 저장한다.
- 미체결 재시도: 주문 후 n분이 지나도 체결되지 않거나 체결 상태를 알 수 없으면, 미체결 조회 후 취소하고 재주문한다. 대기 시간 n, 최대 재시도 횟수, 재주문 가격 정책은 이 단계에서 정하고 `docs/decisions.md`에 기록한다. 최종 실패 시 알림.
- 흐름: 계획 알림 -> 직전 알림(대기 시간 설정) -> 주문 -> 체결 확인(재시도 포함) -> 체결 알림.
- 모든 주문과 실패를 DB와 `output/`에 기록한다.

### 6단계: 납입 관리 (월 150만원 + 추가 납입)
- 설정 `MONTHLY_AMOUNT=1500000`(기본값). DB `contributions`에 납입 내역(정기/추가, 금액, 날짜, 사용 여부)을 기록한다.
- 추가 납입: 여윳돈이 생기면 CLI/API로 금액을 등록한다. 미사용 추가 납입금은 다음 월초 실행에 합산하거나, "지금 즉시 매수"(수동매수)로 바로 계획을 만들 수 있다. 같은 안전장치와 알림을 거친다.

### 7단계: 작업 명령과 OS 스케줄러
- `backend/src/jobs/`에 `run_monthly` 명령을 만든다. 짧게 끝나는 프로세스로, API 서버와 별개로 실행되며 5단계의 주문 실행 서비스를 호출한다.
- OS 스케줄러(Windows 작업 스케줄러, cron, systemd 중 환경에 맞는 것)에 등록하는 방법을 문서화한다.
- 따라잡기: 실행 시점에 이번 달 자동매수 체결 기록이 없고 첫 영업일 이후이면 실행한다. PC가 꺼져 있던 경우를 대비해 부팅/로그인 시와 하루 한 번 실행하도록 등록한다.
- 중복 방지는 5단계의 DB 제약에 의존하므로 여러 번 호출되어도 안전하다. 같은 달에 두 번째 호출이 막히는지 검증한다.

### 8단계: API
- `backend/src/api/`: 목표 비중, 보유/비중 현황, 다음 매수 계획, 추가 납입 등록, 수동매수, 실행·체결 이력.

### 9단계: React 대시보드
- `frontend/src/components/`: 목표 비중 편집, 현재 vs 목표 비중, 다음 매수 계획, 추가 납입 입력, 이력.

### 10단계: 실전 전환
- 모의투자로 최소 2회 월 사이클 검증, 상한/알림 확인 후 체크리스트를 문서화하고 전환한다.

## 추후 발전 방향
- 목표 비중에서 지나치게 괴리된 종목의 매도 후 재분배
- 매수량 계산의 오차 기준을 상대 오차로 바꾸는 방안 검토
- 텔레그램 명령(`/buy 금액` + 확인 버튼)으로 추가매수. 내 chat id만 허용한다.
- 항상 켜진 서버로 이전. 프론트만 Vercel에 배포하는 구성도 검토(백엔드는 SQLite와 장시간 실행 때문에 부적합)
- ISA 연간 납입한도 검사와 납입 플래닝
