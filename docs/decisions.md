# 의사결정 기록

형식:
```
## D-번호. 제목 (YYYY-MM-DD)

- 검토한 대안:
```

## D-001. frontend/backend를 src의 상위에 둔다 (2026-11-17)
- 결정: `frontend/`, `backend/`를 루트에 두고 각각 안에 `src/`를 둔다. `package/` 폴더는 두지 않는다.
- 근거: 프론트와 백은 의존성 파일, 빌드, 배포가 각각 독립적이다.
- 검토한 대안: `src/` 아래에 frontend/backend를 두는 단일 앱 구조. 의존성이 하나인 작은 프로젝트에 적합하나, 따로 배포하기 어려워 제외.

## D-002. memory를 최상단에 두고 인덱스+주제별 파일로 관리한다 (2026-11-17)
- 결정: `memory/memory.md`에는 설명과 링크만 두고, 상세 기록은 주제별 파일로 분리한다. `CLAUDE.md`에서 `@memory/memory.md`로 참조한다.
- 근거: `.claude/memory/`는 Claude Code가 자동으로 읽는 위치가 아니라 `CLAUDE.md` 참조가 필요하다. 인덱스만 로드하면 컨텍스트를 아낄 수 있다.

## D-003. log.md 기록을 Stop 훅으로 강제한다 (2026-11-17)
- 결정: 응답 종료 시 `docs/log.md`보다 나중에 수정된 파일이 있으면 종료를 막고 기록을 요구한다.
- 근거: 규칙 문서는 Claude의 판단에 의존하지만 훅은 하네스가 실행하므로 누락을 막을 수 있다. git 커밋이 없어도 동작하도록 git 대신 파일 수정 시각을 비교한다.
- 검토한 대안: 규칙 문서만 두는 방식(누락 가능), 파일 수정마다 실행하는 PostToolUse 훅(너무 잦아 방해됨).

## D-004. 로그 훅을 Claude의 Edit/Write 기준으로 변경한다 (2026-11-17)
- 결정: PostToolUse(Edit|Write) 훅이 `.claude/.log-pending` 표식을 갱신하고, Stop 훅은 이 표식이 `docs/log.md`보다 새로울 때만 종료를 막는다. D-003의 파일 수정 시각 비교 방식을 대체한다.
- 근거: D-003 방식은 `__pycache__`, DB, `output/`, IDE·사용자의 직접 수정까지 감지해 과도하게 막고, 의미 없는 로그를 쌓게 한다. Claude가 한 작업만 추적하면 이를 피한다. 제외 경로 목록을 따로 관리할 필요도 없다.
- 한계: Bash로 한 변경(mkdir, mv 등)은 감지하지 못한다. 이는 문서화 규칙에 따라 직접 기록한다.
- 검토한 대안: 제외 경로 목록 추가(관리 부담, 사용자 수정 문제 지속), 차단 없이 알림만(누락 방지 못함).

## D-006. Sonnet(구현)/Opus(독립 검토) 2세션 운영과 handoff 방식 (2026-11-17)
- 결정: 구현은 Sonnet Medium, 리뷰는 Opus High로 나눈다. compact 전에 `/handoff`로 `memory/handoff.md`를 수동 작성하고, compact 직후 `SessionStart` 훅이 이를 주입하도록 한다(예정). Opus 리뷰에는 handoff를 넘기지 않는다.
- 근거: 훅은 스킬을 호출하거나 Claude에게 글을 쓰게 할 수 없어 작성 단계를 자동화할 수 없다. 전달 단계만 자동화한다. 리뷰어가 구현자의 맥락을 물려받으면 독립성이 떨어진다.
- 검토한 대안: PreCompact 훅으로 compact를 차단하고 handoff를 강제(자동 compact 시 작업이 멈출 위험).
- 비고: D-005는 ISA 지원 확인용으로 비워 둔다.

## D-007. 주석을 최소화하고 규칙 파일로만 관리한다 (2026-11-17)
- 결정: `.claude/rules/coding-style.md`에 주석 규칙을 둔다. 코드만으로 알 수 없는 사실만 허용하고, 한계·이후 구현·변경 경위를 쓰는 주석은 금지한다. 훅·린터 같은 강제 장치는 두지 않는다.
- 근거: 주석이 에이전트의 변명 창구로 쓰일 수 있고, 사람의 리뷰가 제한적이라 잘못된 주석의 비용이 이익보다 크다. 과도한 하네스가 모델 성능을 떨어뜨릴 수 있어 강제 장치는 실제로 어길 때 추가한다.
- 검토한 대안: 패턴 검사 훅, 린트 규칙(위반이 반복되면 도입).

## D-005. ISA 계좌 API 주문 지원 확인 (2026-11-17)
- 결정: ISA 계좌의 API 주문 지원 여부를 확인했고, 계획대로 진행한다.
- 근거: 사용자가 직접 확인함.

## D-008. handoff 스킬과 훅을 도입하지 않는다 (2026-11-17)
- 결정: handoff 스킬과 `SessionStart`/`PreCompact` 훅을 두지 않는다. D-006의 handoff 부분을 대체한다. 컨텍스트가 커지면 결정을 `decisions.md`와 `memory/`에 남기고 `/compact`한다.
- 근거: 아직 발생하지 않은 문제에 대한 대비라 과하다. 하네스가 과하면 모델 성능에 부담이 될 수 있다.
- 검토한 대안: 수동 `/handoff` + 자동 주입 훅(필요가 확인되면 재검토).

## D-009. 매수 계획 계산 알고리즘 (2026-11-17)
- 결정: 총 평가액 = 보유 + 투입 현금, 종목별 목표금액 = 총 평가액 × 목표비중, 부족금액 = 목표금액 - 현재금액, 매수량 = floor(부족금액 / 주당가격). 부족금액이 음수인 종목은 매도하지 않고 현재금액으로 고정한 채 나머지 종목의 비중을 재조정해 반복 계산한다. 잔여 현금은 남은 부족금액이 큰 종목부터 1주씩 배분하고 동률이면 종목코드 순이다. 상세는 `docs/plan.md` 2단계.
- 근거: 모든 단계가 결정적이라 스크립트화와 테스트가 가능하다.
- 검토한 대안: 양수 부족분을 비례 축소하는 방식(최종 비중이 목표와 더 어긋난다).
- 추후: 지나친 괴리 종목의 매도 후 재분배.

## D-010. 중복 실행 방지는 자동/수동을 구분하고 체결 기록을 기준으로 한다 (2026-11-17)
- 결정: 실행 기록에 `auto`/`manual` 종류를 두고, 월 1회 제한은 `auto`에만 적용한다. 수동매수는 요청 단위 중복만 막는다. 판단은 실행 기록이 아니라 주문번호·체결수량·체결가를 담은 체결 기록으로 한다. 미체결 재시도 정책은 5단계에서 정한다.
- 근거: 자동매수가 실행된 달에는 수동 추가매수가 막히는 문제를 피한다. 실행 기록만으로는 실제 체결 여부를 알 수 없다.

## D-011. 로그 훅을 제거하고 기능 단위 기록 규칙으로 바꾼다 (2026-11-17)
- 결정: Stop/PostToolUse 로그 훅과 `.claude/hooks/`를 제거한다. 로그는 `.claude/rules/documentation.md`의 규칙에 따라 기능·단계 단위로 기록한다. D-003, D-004를 대체한다.
- 근거: 훅이 단순 수정에도 로그를 요구해 과도하다. 하네스가 늘면 모델 성능에 부담이 될 수 있다.
- 검토한 대안: 훅 유지(과함), 훅 범위 축소(관리 부담 지속).

## D-012. 매수량 계산을 1주씩 한계 개선 매수로 바꾼다 (2026-11-17)
- 결정: D-009의 내림 후 잔여 현금 배분과 음수 종목 재조정 반복을 대체한다. 총액을 고정하고, 목표금액과의 절대금액 오차(제곱합)가 가장 많이 줄어드는 종목을 1주씩 매수한다. 개선이 없거나 현금이 모자라면 멈추고 잔여 현금은 이월한다. 상세는 `docs/plan.md` 2단계.
- 근거: 기존 방식은 부족금액이 주당가격보다 작아도 1주를 사서 목표를 넘기는 괴리가 생긴다. 새 방식은 부족금액이 주당가격의 절반을 넘을 때만 사고, 초과 종목이 자동으로 제외되어 재계산 반복이 필요 없다.
- 검토한 대안: 상대 오차 기준(비중이 작은 종목에 민감, 추후 검토), 기존 방식 유지.

## D-013. 기술 스택 확정 (2026-11-17)
- 결정: Python, FastAPI, SQLite + SQLAlchemy, React, OS 스케줄러. APScheduler는 사용하지 않는다. uv, pytest, ruff, pydantic-settings, Vite + TypeScript는 제안으로 두고 1단계에서 확정한다.
- 근거: Python은 증권사 참고 코드(`docs/reference/`)가 Python이라 재사용할 수 있다. SQLite는 사용자 1명, 소량 쓰기라 충분하고 트랜잭션과 유니크 제약으로 중복 방지가 가능하다. SQLAlchemy는 성숙하고 마이그레이션 도구가 있다.
- 검토한 대안: TypeScript(KIS 클라이언트 재작성 필요), Flask/Django, PostgreSQL(서버 운영 과함), 순수 sqlite3, SQLModel, Next.js, HTMX.
- Vercel: 프론트 배포에는 가능하나 백엔드에는 부적합하다. 파일 시스템이 영구적이지 않아 SQLite를 쓸 수 없고, Cron은 시각이 부정확하며, 주문 후 체결 대기·재시도를 한 번의 함수 호출로 처리하기 어렵다. 주문 가능한 API를 공개하는 보안 부담도 있다.

## D-014. 프로세스 분리와 OS 스케줄러, LLM 미사용 (2026-11-17)
- 결정: API 서버와 작업 명령(`run_monthly`)을 별도 프로세스로 두고, 작업 명령은 OS 스케줄러가 호출한다. 실행 시점에 이번 달 자동매수 기록이 없으면 실행하는 따라잡기 방식을 쓴다. 실행 환경은 내 PC로 시작한다. LLM은 사용하지 않는다.
- 근거: 서버가 재시작되거나 죽어도 월초 매수가 영향을 받지 않고, 워커가 여러 개일 때의 중복 실행이 없다. 작업을 손으로 실행해 테스트하기 쉽다. PC가 꺼져 있어도 켠 뒤 따라잡을 수 있다. 돈이 나가는 작업에서 LLM 해석의 오류 위험과 비용을 피한다.
- 검토한 대안: 서버 안의 APScheduler(재시작 시 누락, 중복 실행), GitHub Actions(영구 DB 부재), 텔레그램 자연어 명령(오해석 위험).
